# UniVRM 0.131.x の正式版をすべて受け付ける

- 日付: 2026-10-18
- 対象: `Compatibility/dependencies.json`・`Tools/generate-compatibility.py`・`Editor/Compatibility/DependencyPolicy*.cs`・両 asmdef・`Editor/LilToonExporterWindow.cs`・`Tools/DependencyCompatibilityTests.cs`・README 3 種・`Compatibility/README.md`・`Editor/Vrm10AppearanceExporter.cs`・`Tests/Editor/MorphNormalExportTests.cs`・`Tools/run-unity-compatibility.py`・`Compatibility/Evidence/UniVrm0131x/`・`CHANGELOG.md`

## 背景

UniVRM 0.131.3 が 2026-10-02 に公開された。VPM の依存は `0.131.x` なので VCC・ALCOM は 0.131.3 を入れるが、Exporter は 0.131.0／0.131.1／0.131.2 を名前で列挙して完全一致を見ていたため、0.131.3 では書き出しの前に止まっていた。版の判定は `dependencies.json`・生成した `DependencyPolicy.Generated.cs`・asmdef の `versionDefines`・実行時の検査・README の 5 か所にあり、パッチが出るたびに全部を直す必要があった。

オーナーから、UniVRM 0.131.x はすべて対応すること、UniVRM を同梱・埋め込みせず利用者のプロジェクトの UniVRM を参照する今の方式を続けることの 2 点の指示があった。

## 決定

- 受け付ける範囲を「0.131 系の正式版すべて」にする。asmdef の `versionDefines` は UniGLTF と VRM のそれぞれで `[0.131.0,0.132.0)` の 1 つにし、定義名は `VRVLOG_VRM_0_131`・`VRVLOG_GLTF_0_131` にする（以前はパッチごとに定義を作って OR していた）。
- 実行時の検査（`DependencyPolicy.SupportsUniVrm`）は、`X.Y.Z` の数字だけの版で、メジャーとマイナーが `0.131` のものを通す。プレリリース・ビルドメタデータ付き・0.132 以降は従来どおり止める。UniGLTF と VRM が別の版のときも止める。
- `uniVrm.versions` は「公式ソースのコミットで実際に確かめたパッチの一覧」として残し、0.131.3（`9750dadc592f421c356bf0376c73e61abbe323e3`）を足す。検証ツール（`run-unity-compatibility.py`・`create-liltoon-version-projects.py`）はこの一覧の版だけを検証対象にする。
- 対応範囲の表示（Exporter の画面・エラー文・README）は `0.131.x` にし、確かめた版を括弧で添える。
- UniVRM の同梱・埋め込みはしない。VPM の依存は `0.131.x`・`releaseVersion` は `0.131.0` のまま変えない。
- 表情の法線を補う `PreserveMorphNormals` は、BlendShape ごとに新しい法線配列を確保して UniVRM へ渡す。0.131.3 で `NativeArrayManager.CreateNativeArray(T[])` が配列をコピーせず包むようになったため（下記）。
- 1 つのメッシュに法線の違う BlendShape が複数ある場合を確かめる回帰テスト `MorphNormalExportTests.EveryMorphOfOneMeshKeepsItsOwnAuthoredNormals` を足し、`exporter-behavior` の必須ケースに `MorphNormalExportTests` を加える。

## 確認したこと

- 0.131.2 と 0.131.3 の公式ソースを比べた。Exporter が使う `ModelExporter`・`MeshWriter`・`BuiltInVrm10MaterialExporter` に差はない。`Vrm10Exporter` の差は spring bone の角度制限（`VRMC_springBone_limit`）だけで、`specVersion: "1.0-draft"` が付くことと、子を持たない末端の joint には制限を書かないことの 2 点。末端の joint は揺れの向きを決める側ではないので、制限が無くても動きは変わらない。
- ただし `NativeArrayManager.CreateNativeArray(T[])` と `CreateNativeArray(ArraySegment<T>)` が、0.131.3 では `CreateNativeArray(ReadOnlyMemory<T>)` を経由し、元の配列を固定して `NativeArray` として包むだけになった（0.131.2 まではコピーしていた）。`PreserveMorphNormals` は 1 つの法線配列を全 BlendShape で使い回していたので、0.131.3 では全 BlendShape の法線が最後の BlendShape の値を指し、`MeshWriter` が「法線の差分なし」と判断した BlendShape は glTF の `NORMAL` 自体が落ちた。実プロジェクトの `exporter-integration` で `MissingMeshAttributesTests.NormalExporterPreservesMissingAttributeMeshesThroughRealVrmRoundTrip` の 6 ケースが 0.131.3 だけ失敗し、同じ入力の書き出しでも 0.131.2 は全ターゲットに `NORMAL` があり 0.131.3 は先頭のターゲットに無いことを GLB で確かめた。BlendShape ごとに配列を確保すると、この 6 ケースは 0.131.3 でも通り、lilToon の書き出し比較（63 件）は修正の前後と 0.131.2／0.131.3 の間で `asset.generator` 以外一致した。
- Unity 2022.3.22f1 で、UniVRM 0.131.0／0.131.2／0.131.3 を入れた実プロジェクト 4 つで `exporter-integration`（`compatibility` と `exporter-behavior` を含む）を、0.131.2 と 0.131.3 の組で lilToon の書き出し比較を行った。0.131.1 は以前から一覧にある版で、今回の実プロジェクトでは確かめていない。版の組み合わせと結果は `Compatibility/Evidence/UniVrm0131x/README.md` に書いた。

## 検討した代替案と不採用理由

- 0.131.3 だけを一覧に足す: 次のパッチでまた止まり、利用者は VCC が選んだ版を手で戻すことになる。オーナーの指示（0.131.x 全部）とも合わない。
- 0.130 以前まで広げる: 0.130 は角度制限を書き出さず、0.128 以前は `VRM10SpringBoneJoint.m_anglelimitType` が無いため Exporter がコンパイルできない。0.125 以前は `ModelExporter.Export` の引数も違う。版ごとの分岐が必要になり、PhysBone の見た目が版で変わるので見送る。
- UniVRM を同梱する: オーナーの指示で行わない。利用者のプロジェクトの別ツールと UniVRM が二重になる。

## 影響

- 将来の 0.131.4 以降は、確かめる前から書き出せる。Exporter が呼ぶ UniVRM の API の引数が変わればバックエンドがコンパイルされず、診断画面に出る。引数が同じまま挙動が変わった場合は、その版を確かめるまで気づけない。0.131.3 の配列の扱いの変更がその例で、コンパイルは通り、表情の法線だけが黙って変わった。新しいパッチが出たら `exporter-behavior` を回してから `uniVrm.versions` に足す。
- 0.132 以降は従来どおり止まり、新しい adapter が必要になる。
