# UniVRM 0.131.x の正式版をすべて受け付ける

- 日付: 2026-10-18
- 対象: `Compatibility/dependencies.json`・`Tools/generate-compatibility.py`・`Editor/Compatibility/DependencyPolicy*.cs`・両 asmdef・`Editor/LilToonExporterWindow.cs`・`Tools/DependencyCompatibilityTests.cs`・README 3 種・`Compatibility/README.md`・`Editor/Vrm10AppearanceExporter.cs`・`Tests/Editor/MorphNormalExportTests.cs`・`Tools/run-unity-compatibility.py`・`Tools/create-liltoon-version-projects.py`・`Tools/unity_packages.py`・`Tools/test-compatibility-tooling.py`・`Compatibility/Evidence/UniVrm0131x/`・`CHANGELOG.md`

## 背景

UniVRM 0.131.3 が 2026-10-02 に公開された。VPM の依存は `0.131.x` なので VCC・ALCOM は 0.131.3 を入れるが、Exporter は 0.131.0／0.131.1／0.131.2 を名前で列挙して完全一致を見ていたため、0.131.3 では書き出しの前に止まっていた。版の判定は `dependencies.json`・生成した `DependencyPolicy.Generated.cs`・asmdef の `versionDefines`・実行時の検査・README の 5 か所にあり、パッチが出るたびに全部を直す必要があった。

オーナーから、UniVRM 0.131.x はすべて対応すること、UniVRM を同梱・埋め込みせず利用者のプロジェクトの UniVRM を参照する今の方式を続けることの 2 点の指示があった。

## 決定

- 受け付ける範囲を「0.131 系の正式版すべて」にする。asmdef の `versionDefines` は UniGLTF と VRM のそれぞれで `[0.131.0,0.131.999999999]` の 1 つにし（上限を `0.132.0)` の開区間にすると、セマンティックバージョニングで正式版より前に並ぶ `0.132.0-preview` などが範囲に入るおそれがあるため、0.131 の中で閉じる。999999999 は生成スクリプトが受け付けるパッチ番号の上限）、定義名は `VRVLOG_VRM_0_131`・`VRVLOG_GLTF_0_131` にする（以前はパッチごとに定義を作って OR していた）。
- 実行時の検査（`DependencyPolicy.SupportsUniVrm`）は、`X.Y.Z` の数字だけの版で、メジャーとマイナーが `0.131` のものを通す。プレリリース・ビルドメタデータ付き・0.132 以降は従来どおり止める。UniGLTF と VRM が別の版のときも止める。
- `uniVrm.versions` は「公式ソースのコミットで実際に確かめたパッチの一覧」として残し、0.131.3（`9750dadc592f421c356bf0376c73e61abbe323e3`）を足す。検証ツール（`run-unity-compatibility.py`・`create-liltoon-version-projects.py`）は、書き出し時の検査と同じく 0.131 系の正式版をすべて検証対象にする。一覧に無いパッチを一覧に足す前に `exporter-behavior` まで回せるようにするため。一覧にあるかどうかは `run-unity-compatibility.py` の結果 JSON に `uniVrmListed` として残す。検証用プロジェクトの生成も一覧で絞らない（絞ると、一覧に足す前の版で lilToon の書き出し比較ができない）。
- 対応範囲の表示（Exporter の画面・エラー文・README）は `0.131.x` にし、確かめた版を括弧で添える。
- UniVRM の同梱・埋め込みはしない。VPM の依存は `0.131.x`・`releaseVersion` は `0.131.0` のまま変えない。
- 表情の法線を補う `PreserveMorphNormals` は、BlendShape ごとに新しい法線配列を確保して UniVRM へ渡す。0.131.3 で `NativeArrayManager.CreateNativeArray(T[])` が配列をコピーせず包むようになったため（下記）。
- 1 つのメッシュに法線の違う BlendShape が複数ある場合を確かめる回帰テスト `MorphNormalExportTests.EveryMorphOfOneMeshKeepsItsOwnAuthoredNormals` を足し、`exporter-behavior` の必須ケースに `MorphNormalExportTests` を加える。

## 確認したこと

- 0.131.2 と 0.131.3 の公式ソースを比べた。Exporter が使う `ModelExporter`・`MeshWriter`・`BuiltInVrm10MaterialExporter` の 3 つには差がない。ほかに差があったもののうち、`GlbChunk`（`Bytes` の型が `ArraySegment` から `ReadOnlyMemory` に変わった。公開 API の変更）・`GltfData`・JSON パーサー・`Vrm10Importer` は、書き出しの経路からは呼ばない（書き出しは `ExportingGltfData` を使う）。読み込み側で Exporter が呼ぶのは `Vrm10.LoadBytesAsync` だけで、使うのはテストと書き出し後の比較画面（`ExportRecoveryComparisonWindow`）。0.131.3 の実プロジェクトでは、これらを含めてコンパイルとテストが通った。`Vrm10Exporter` の差は spring bone の角度制限（`VRMC_springBone_limit`）だけで、`specVersion: "1.0-draft"` が付くことと、子を持たない末端の joint には制限を書かないことの 2 点。末端の joint は揺れの向きを決める側ではないので、制限が無くても動きは変わらない。
- ただし `NativeArrayManager.CreateNativeArray(T[])` と `CreateNativeArray(ArraySegment<T>)` が、0.131.3 では `CreateNativeArray(ReadOnlyMemory<T>)` を経由し、元の配列を固定して `NativeArray` として包むだけになった（0.131.2 まではコピーしていた）。`PreserveMorphNormals` は 1 つの法線配列を全 BlendShape で使い回していたので、0.131.3 では全 BlendShape の法線が最後の BlendShape の値を指し、`MeshWriter` が「法線の差分なし」と判断した BlendShape は glTF の `NORMAL` 自体が落ちた。実プロジェクトの `exporter-integration` で `MissingMeshAttributesTests.NormalExporterPreservesMissingAttributeMeshesThroughRealVrmRoundTrip` の 6 ケースが 0.131.3 だけ失敗し、同じ入力の書き出しでも 0.131.2 は全ターゲットに `NORMAL` があり 0.131.3 は先頭のターゲットに無いことを GLB で確かめた。BlendShape ごとに配列を確保すると、この 6 ケースは 0.131.3 でも通り、lilToon の書き出し比較（63 件）は修正の前後と 0.131.2／0.131.3 の間で `asset.generator` 以外一致した。
- Unity 2022.3.22f1 で、UniVRM 0.131.0／0.131.2／0.131.3 を入れた実プロジェクト 4 つで `exporter-integration`（`compatibility` と `exporter-behavior` を含む）を、0.131.2 と 0.131.3 の組で lilToon の書き出し比較を行った。0.131.1 は以前から一覧にある版で、今回の実プロジェクトでは確かめていない。版の組み合わせと結果は `Compatibility/Evidence/UniVrm0131x/README.md` に書いた。

## 検討した代替案と不採用理由

- 0.131.3 だけを一覧に足す: 次のパッチでまた止まり、利用者は VCC が選んだ版を手で戻すことになる。オーナーの指示（0.131.x 全部）とも合わない。
- 0.130 以前まで広げる: 0.130 は角度制限を書き出さず、0.128 以前は `VRM10SpringBoneJoint.m_anglelimitType` が無いため Exporter がコンパイルできない。0.125 以前は `ModelExporter.Export` の引数も違う。版ごとの分岐が必要になり、PhysBone の見た目が版で変わるので見送る。
- UniVRM を同梱する: オーナーの指示で行わない。利用者のプロジェクトの別ツールと UniVRM が二重になる。

## 影響

- 将来の 0.131.4 以降は、確かめる前から書き出せる。VCC・ALCOM は、利用者が Exporter に触れなくても新しい 0.131.x を入れられる。
- 以前は `defineConstraints` がパッチを名前で列挙していたので、一覧に無いパッチではバックエンドがコンパイル対象から外れ、診断画面が理由を出していた。今回からバックエンドはどの 0.131.Z に対してもコンパイルされる。Exporter が呼ぶ UniVRM の API のシグネチャが将来のパッチで変わると、利用者のプロジェクトでこのパッケージのコンパイルエラーになり、診断画面には出ない。開いているエディタではスクリプトの再読み込みが止まり、プロジェクトを開き直すと Unity が Safe Mode を勧め、コンパイルエラーがある間は VRChat SDK がビルドを拒む。パッチでも公開 API は変わる。0.131.2 から 0.131.3 では `GlbChunk.Bytes` の型が `ArraySegment` から `ReadOnlyMemory` に変わった（Exporter は使っていない）。
- シグネチャが同じまま挙動が変わった場合はコンパイルが通り、その版を確かめるまで気づけない。0.131.3 の配列の扱いの変更がその例で、表情の法線だけが黙って変わった。
- 対策として、新しい 0.131 のパッチが出たらすぐに `compatibility`・`exporter-behavior`・`exporter-integration` で確かめ（検証ツールは一覧に無い 0.131 の正式版も受け付ける）、通れば公式ソースのコミットとともに `uniVrm.versions` に足す。壊れていれば Exporter の修正版か、そのパッチを範囲から外した版を出す。新しいリリースの有無は `Tools/check-upstream-dependencies.py`（手動実行）で分かる。
- 残課題: 最新の 0.131.x タグに対して Exporter を定期的にコンパイルする CI を足すと、上の確認を待たずに壊れたことが分かる。ワークフローの変更はオーナーの承認が要るため、この PR では行わず後続にする。
- 0.132 以降は従来どおり止まり、新しい adapter が必要になる。
