# 8-bit の法線画像を、方向の差が閾値に収まるときだけ rgba32 で保存する

- 日付: 2026-10-21
- 対象: `Editor/LilToonFullSnapshot.cs`・`Tests/Editor/NormalStorageTests.cs`・`Tests/Editor/FullTextureResizeTests.cs`・`Tests/Editor/ExportVrmLilToonPreviewTests.cs`・`Tests/Editor/LilToonFullExportTests.cs`・`Documentation~/NormalTextureFiltering.md`・`CHANGELOG.md`

## 背景

Full lilToon の拡張（`VRVLOG_materials_liltoon`）は、法線画像を `UnpackNormal` でデコードした canonical 値で保存している。元が 8-bit / 圧縮の法線画像も、iPhone の GPU が RGBA32Float を補間できない問題（`NormalTextureFiltering.md`）のあとは `rgbaHalf` で保存している。

`rgbaHalf` は 1 画素 8 バイトで、`rgba32` の 2 倍になる。書き出し済みの VRM 24 個に含まれる法線画像 64 枚は、`rgbaHalf` で計 95.51 MB あった。元が 8-bit の画像なら、canonical 値も多くは 8-bit の値そのものなので、Half で持つ意味は薄い。ただし縮小時の面積平均、BC 圧縮の展開、AG 形式で R に A を掛ける処理では 8-bit の値の間に来るので、丸めると方向が変わる。変わる量は、アプリが RG から方向を出すときに掛ける強度（`_BumpScale` など）が大きいほど、また面に対して浅い方向ほど大きくなる。

## 決定

- 閾値を先に決めた。全 face・全 mip の画素で、Half の値と 8-bit に丸めた値（`round(clamp01(v) * 255)`）からアプリと同じ式で方向を出し、その角度差の 99 パーセンタイル（nearest-rank）が 0.5 度以下、かつ最大が 2.0 度以下なら `rgba32` で保存する。外れたら従来どおり `rgbaHalf`。この閾値は実際のアバターを測る前に決め、測った結果を見て動かしていない。
- 方向の式はアプリと同じ `xy = (rg * 2 - 1) * s`、`z = sqrt(1 - saturate(dot(xy, xy)))`。`s = max(1, |scale|)` で、scale は `_BumpMap` → `_BumpScale`、`_Bump2ndMap` → `_Bump2ndScale`、`_MatCapBumpMap` → `_MatCapBumpScale`、`_MatCap2ndBumpMap` → `_MatCap2ndBumpScale` から取る。機能のトグルがオフでも使う（あとでオンにされても見た目が変わらないように）。
- 同じ画像を複数の参照が使うときは、最も大きい `s` で決める。`LilToonFullSnapshot` が画像ごとにそれまでの最大の `s` を覚え、あとの参照で大きくなったときだけ GPU から Half で読み直して決め直す。チャンクの数は変わらないので、同じ位置のデータを差し替える。上の 4 つ以外の法線プロパティ（アウトラインやファーのベクトル、異方性の接線）は RG からこの式で読まれず誤差を見積もれないので、そこから参照される画像は `rgbaHalf` のままにする。Unity の既定法線画像は未設定の異方性の接線などからも参照されるので、`rgbaHalf` のまま。
- 対象は `StorageFormat` が法線だという理由だけで `rgbaHalf` を選んだ画像に限る。元が Half・Float・16-bit normalized・EAC の法線画像、法線以外の画像、PNG と MToon 側は変えない。Float を避ける既存の決定もそのまま。
- `rgba32` にした画像も `normal: true` を残す。バイト列は `LilToonFullContract.ValidatePixels(..., "rgba32")` を通してから書く。
- 判定の前に 1 枚分の Half の mip チェーン全体をメモリに持つ。最大 1024×1024 で約 11 MB。判定のあとは mip ごとに書いて手放す。対象でない画像はこれまでどおり mip ごとに読んで書く。

### アプリとの互換性

アプリの変更は要らない。`rgba32` は schema 2.0 で既に定義されている形式で、アプリは法線を保存形式によらず同じ式でデコードする。schema 2.0 を読めない古いアプリは、今の書き出しをそもそも読み込めないので、この変更で新たに読めなくなる組み合わせはない。

## 入れなかったもの

- 8-bit / 圧縮の法線画像を、誤差を測らずにすべて `rgba32` にすること。上の 64 枚のうち 1 枚は最大の角度差が 2.13 度で、閾値の 2.0 度を超えた。
- R と G だけの 2 チャンネル形式。データはさらに半分になるが、schema に新しい形式の値が要る。古いアプリの厳密な検査はその値を拒否するので、読み込めないファイルになる。

## 確認したこと

- 閾値を決めたあとで、上の 64 枚を測った。63 枚は 99 パーセンタイルが 0.074 度以下、最大が 1.374 度以下で、`rgba32` になる。残る 1 枚は最大が 2.13 度で `rgbaHalf` のまま。63 枚を `rgba32` にすると計 22.7 MB 減る。
- `NormalStorageTests` を足した。滑らかな法線は `rgba32` になること、浅い方向で最大が 2 度を超えると `rgbaHalf` のままになること、中くらいの傾きは強度 1 で通り強度 8 / 9.6 / -9.6 で落ちること、99 パーセンタイルの境界、強度が分からない参照、強い参照と弱い参照の両方の順序、実際の書き出しで全 mip のチャンクの大きさと拡張全体の検査が通ることを見る。
- 8-bit の法線画像を `rgbaHalf` と決め打ちしていた `FullTextureResizeTests` と `ExportVrmLilToonPreviewTests` の期待値を、`rgba32` と 8-bit の丸め幅に合わせて直した。
- ホスト検証（`Tools/run-validation.py`）と名前の検査（`Tools/check-names.py`）が通った。
- Unity 2022.3 の EditMode で `NormalStorageTests`・`FullTextureResizeTests`・`ExportVrmLilToonPreviewTests`・`LilToonFullExportTests`・`LilToonFullRenderTests` の 230 件を回し、102 件が通過、失敗は 0 件だった。残る 128 件は、アプリのシェーダーやアプリと合わせた検証用プロジェクトが要るテストで、テスト用のプロジェクトでは skip になる。
- 見た目の比較: 24 体を変更の前と後で書き出し、アプリの VRM の読み込み処理と公式の lilToon で、正面の全身・顔・斜め 45 度の 3 方向を 1024×1024 で描いて比べた。全員が Full lilToon で読み込まれ、どの画像でも画素の差は最大 2/255、8/255 を超える画素は 0 だった。PSNR は顔で 73.7 dB 以上、全身で 81.8 dB 以上（同じ画像になった 4 体は無限大）。
