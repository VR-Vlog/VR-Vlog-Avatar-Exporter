# アルファが全面 0 の画像は縮小しても色を保つ

- 日付: 2026-11-09
- 対象: `Editor/TextureResizePolicy.cs`、`Editor/LilToonFullTexture.cs` の `ReadResized`

## 背景

色の画像を縮小するときは、透過の縁に透明な画素の色が混ざらないようアルファで重みを付けて平均している。元の画素のアルファがすべて 0 だと重みの合計が 0 になり、RGB は黒で出力されていた。

RGB に色を入れてアルファを 0 のままにした画像は、不透明のマテリアルでは Unity 上で色どおりに見える。この画像が上限より大きいと、書き出しの縮小で真っ黒になっていた。標準 VRM の画像（CPU の縮小）と lilToon の拡張の画像（GPU の縮小）の両方で起きる。

## 決定

画像全体のアルファが 0 のときだけ、アルファの重みを使わずに色を平均する。アルファは 0 のまま出力する。

CPU の縮小は入力のアルファを先に調べる。GPU の縮小は今までどおりに読み出し、結果のアルファが全面 0 のときだけ、アルファの重みなしで読み直す。線形の画像・法線・HDR・Half は今までの処理のままにする。

1 画素でもアルファがある画像は、CPU も GPU も今までと同じ計算になるので出力は変わらない。全面アルファ 0 の画像は透過のマテリアルでは何も描かれないので、色を保っても見た目は悪くならない。

## 検討した代替案と不採用理由

- 縮小先の画素ごとに、重みの合計が 0 ならそこだけ色の単純平均にする: 透過の画像で、元は不透明の画素に隣り合っていない透明な部分の色が、縮小で縁に混ざることがある。
- マテリアルの透過の種類を見て、不透明のときだけアルファの重みを使わない: 同じ画像を不透明と透過のマテリアルで共有する場合に、画像を分ける必要があり、設計の変更になる。

## 残る制限

画像の一部だけアルファが 0 で、それを不透明のマテリアルで使う場合は、その部分が縮小で黒くなる動作のまま残る。直すには上の 2 つ目の代替案が要る。

## 確かめたこと

`FullTextureResizeTests.ResizedImagesWithoutAlphaKeepTheirColor` は CPU・GPU それぞれの修正を外すと sRGB のケースが失敗し、修正後に通る。同じテストで、1 画素だけアルファがある画像の透明な部分は従来どおり黒いことも固定する。`FullTextureResizeTests` の 27 件が GPU ありの Unity 2022.3 で通る。
