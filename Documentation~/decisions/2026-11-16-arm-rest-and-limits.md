# 腕の rest を元のヒューマノイドの T ポーズにそろえ、肩と腕の動く範囲を書き出す

- 日付: 2026-11-16
- 対象: `Editor/AvatarRestPose.cs`、`Editor/HumanoidLimitCapture.cs`、`Formats/Runtime/HumanoidLimitData.cs`

## 背景

腕を下げた初期姿勢（A ポーズ）のアバターを書き出すと、アプリの待機やエモートで腕が元のアバターより体側へ寄り、肘の曲がり方も元と違っていた。元のアバター（Unity のヒューマノイドで同じクリップを再生したもの）と書き出した VRM（UniVRM で読み、アプリと同じく筋肉値で再生したもの）を比べると、原因は 2 つあった。

1. **rest の腕の形が元のヒューマノイドの T ポーズと違う。** 書き出しは下がった腕を外向きにまっすぐ上げていた。元のヒューマノイドの T ポーズは上腕が少し下がり、肘も少し曲がっている。筋肉値は VRM の rest（T ポーズ）からの差として腕を回すので、この差はどの動きにも残る。
2. **肩と腕の動く範囲が既定値に戻る。** UniVRM は読み込んだ VRM のヒューマノイドを Unity の既定の範囲で作り直す。元のアバターが肩の範囲を狭めていると（例: 上下 0〜35 度。既定は -15〜30 度）、同じ筋肉値でも肩の回り方が変わり、上腕ごと腕が下がる。

## 決定

### 腕は、元のヒューマノイドの T ポーズの回転を取る

`AvatarRestPose.AlignArm` で腕を上げるときは、上腕・前腕・手に、元のアバターのヒューマノイドの `skeleton` が持つ T ポーズの回転（親から見た回転）をそのまま与える。向きだけでなく、ねじれもそろう。

次のときは今までどおり外向きにまっすぐ上げる。

- ヒューマノイドの `skeleton` に、そのボーンの名前が無い、または同じ名前が 2 つある。
- T ポーズの回転を与えても、腕が上げる対象の角度（`MaximumArmAngle`）を超えて下がったまま、または曲がったままになる。

肩は動かさない。肩のずれは 2 つ目の決定で直す。これは、書き出す肩の回転が元のヒューマノイドの T ポーズの肩と同じアバターでだけ成り立つ。肩を T ポーズから回して置いたアバターでは、上腕の向きがその差の分ずれたまま残る（この変更の前も同じ）。

`2026-11-04-rest-pose-t-pose.md` から変わる点は次の 2 つ。

- 20 度以内に入った前腕は作者の肘の曲げとして残していたが、元のヒューマノイドの T ポーズの曲げにする。
- 手は対象にしていなかったが、手にも T ポーズの回転を与える。上腕と前腕だけをそろえると、手の向きが元の T ポーズからずれて、筋肉値で回す手首の向きが変わるため。

腕を上げる対象（上腕か前腕が 20 度を超えて下がった腕）と、それ以外のアバターの出力は変わらない。

### 肩と腕の動く範囲を `asset.extras` に書き出す

元のヒューマノイドが既定以外の範囲を持つ肩・上腕・前腕・手について、`HumanLimit` の `min`・`max`・`center`・`axisLength` を、VRM 1.0 のボーン名をキーにして `asset.extras["VRVLOG_humanoidLimits"]` に書く。形式は `HumanoidLimitData`、JSON スキーマは `Schema/VRVLOG_humanoidLimits.1.schema.json`。

- 既定の範囲しか持たないアバターでは書かない。そのため、そうしたアバターの出力は変わらない。
- 拡張ではなく `asset.extras` に置き、`extensionsUsed` と `VRVLOG_requiredAppVersions` には載せない。キーを知らないプレイヤーも今までどおり再生できる。
- 範囲が契約の外（角度が ±180 度を超える、`min` が正、など）のときは何も書かず、書き出しの警告に出す。`HumanLimit` の `min` は初期値から負の向きへ、`max` は正の向きへ回せる量なので、`min` は 0 以下、`max` は 0 以上とした。
- 「既定以外」は `HumanLimit.useDefaultValues` が false のものを指す。値が既定と同じでもこのフラグが false なら書く（読む側の結果は同じ）。
- 範囲を読むところ（`HumanoidLimitCapture.Capture`）で失敗したときは書かずに警告に出し、書き出しは続ける。`asset.extras` へ入れるところ（`Inject`）は、リップシンクの `LipSyncCapture.Inject` と同じく書き出しの途中で失敗させる。ここで失敗するのは、書き出した glTF の `asset` が壊れているときだけ。

アプリは、キーがあるときだけ ControlRig のヒューマノイドをこの範囲で作り直す。キーの無い VRM の扱いは変わらない。

## 測った結果

検証環境で、腕を下げた初期姿勢のアバター（素体）を書き出した。アプリに入っている 40 個のクリップを元のアバターと VRM で再生し、15 fps で比べた。差は元のアバターからの差で、平均／最大。

| 条件 | 肩の向き | 上腕の向き | 前腕の向き | 手の位置 |
|---|---|---|---|---|
| 修正前 | 12.7 度／23.6 度 | 10.4 度／21.1 度 | 11.0 度／23.1 度 | 7.2 cm／16.7 cm |
| 動く範囲だけ | 0.0 度／0.0 度 | 2.4 度／2.6 度 | 4.8 度／9.1 度 | 2.3 cm／3.6 cm |
| rest だけ | 12.7 度／23.6 度 | 12.3 度／23.3 度 | 11.3 度／23.4 度 | 8.3 cm／17.6 cm |
| 両方 | 0.0 度／0.0 度 | 0.0 度／0.0 度 | 0.0 度／0.0 度 | 0.0 cm／0.0 cm |

rest だけでは肩のずれが残って改善しない。両方そろえると、筋肉値で再生する限り元と一致する。

## 直らないもの

VRM Animation（VRMA）を骨の回転として写すプレイヤーでは、動く範囲は使われない。VRMA の回転は書き出した側のヒューマノイドの範囲で決まった姿勢なので、元のアバターの範囲で解いた姿勢とは肩の向きで平均 12 度ほど違う。これは VRMA の再生方法の問題で、このファイルで扱う書き出しでは直せない。

rest を元のヒューマノイドの T ポーズにそろえる変更は、VRMA では手の位置を悪くする。同じアバターで VRMA にした 6 本のクリップを比べた（差は元のアバターからの差で、平均／最大）。

| 条件 | 肩の向き | 肘の曲がる面 | 手のひらの向き | 手の位置 |
|---|---|---|---|---|
| 修正前 | 12.3 度／23.2 度 | 14.3 度／72.0 度 | 12.5 度／24.9 度 | 6.7 cm／13.1 cm |
| 動く範囲だけ | 修正前と同じ（範囲は使われない） | | | |
| rest だけ・両方 | 12.3 度／23.2 度 | 9.7 度／52.0 度 | 10.3 度／20.5 度 | 8.6 cm／16.1 cm |

肘の曲がる面と手のひらの向きは良くなるが、肩のずれが残ったまま上腕と前腕の rest が元の T ポーズに合うので、手は元から遠ざかる。筋肉値で再生するアプリと、骨の回転を写すプレイヤーの両方を同じ rest で良くするには、VRM の rest は従来の T ポーズのまま、元のヒューマノイドの T ポーズを `asset.extras` で渡してアプリ側の `HumanDescription.skeleton` に入れる形が候補になる。試していない。
