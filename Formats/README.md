# VR Vlog Avatar Formats

`com.vrvlog.avatar-formats` is the shared code for the custom data that the exporter writes into a VRM and the VR Vlog app reads back:

- `ExpressionAnimationData` (`VRVLOG_expression_animations`): reads, writes and evaluates expression animation curves. `Read` reads schema 1, where points name dedicated `__VRVlog_Anim_` morphs. `WriteDocument` writes schema 2 (`ExpressionAnimationDocument`), which also lists where each custom expression came from (`menu`, `gesture` or `faceEmo`) and points at morphs by glTF node and morph target index. `ReadDocument` reads both schemas. Schema 2 may carry the optional root key `order`; `source` (`ExpressionAnimationDocument.SourceOrder`) means the exporter wrote the custom expressions in the order players show them: hand gesture faces, FaceEmo faces, the others without bone or visibility changes, then the others with them. `ReadDocument` keeps any text there and ignores a value that is not text, and a player that does not know the value orders the list its own way. Schema 2 may also carry the optional root key `transforms`: for each custom expression, the keys of the glTF node translation, Euler angles, rotation, scale and visibility (`active`) it changes, on the same clock as its `animations` entry. `ReadDocument` ignores it and `ReadTransforms` reads it; a document without bone or visibility changes has no `transforms` key. The exporter writes `transforms` while `ExpressionTransformCurves.Enabled` is on (the default). Schema 2 may also carry the optional root key `presetTransforms`: the bone and visibility pose of a standard VRM expression (`ExpressionAnimationData.PresetTransformNames`: emotions, mouth shapes and blinks; never gaze or neutral), named by preset, held at time 0 (`duration` 0, `loop` false). A player blends it by the expression's weight. `ReadDocument` ignores it and `ReadPresetTransforms` reads it; a document may carry it alone, which readers older than the key reject as empty without losing anything. The exporter writes schema 2 only; `Read` and `ReadDocument` also read schema 1 files, and there is no schema 1 writer. The JSON schemas are `Schema/VRVLOG_expression_animations.1.schema.json` and `.2.schema.json`.
- `ObjectToggleData` (`VRVLOG_object_toggles`): reads and writes the objects that the avatar's VRChat menu toggles switch. Each group is one parameter with its target glTF nodes and their `activeSelf` for each value (always including 0 and the default value); each item is one menu toggle (`id`, `name`, submenu `path`, `parameter`, `value`). `Read` rejects the whole extension when anything is outside the contract, and `Write` runs the same checks. The JSON schema is `Schema/VRVLOG_object_toggles.1.schema.json`.
- `ExpressionGestureData` (`VRVLOG_expression_gestures`): reads and writes the 64-cell table of the custom expressions the avatar's FX shows for each pair of VRChat hand gestures (`Cells[left * 8 + right]`, each `null` or up to 8 references with an optional trigger `drive`). The JSON schema is `Schema/VRVLOG_expression_gestures.1.schema.json`; the format and how the exporter builds the table are in `Documentation~/ExpressionGestures.md`.
- `LipSyncData` (`VRVLOG_lip_sync`): reads and writes how the app mixes the lip sync vowels: `dominantViseme` shows only the strongest vowel, as VRChat's Viseme Parameter Only does, and `transitionSeconds` (0 to 10) is how long a change of that vowel blends. The exporter writes it only for avatars whose Lip Sync is Viseme Parameter Only. The JSON schema is `Schema/VRVLOG_lip_sync.1.schema.json`; the decision is `Documentation~/decisions/2026-10-25-lipsync-dominant-viseme.md`.
- `AvatarAnimatorData` (`VRVLOG_avatar_animator`): reads and writes the avatar's VRChat FX controller, Expression Menu and Expression Parameters as written in the avatar: parameters with their origin, menus, the FX layers (the first at weight 1 and as an override layer, a synced layer with the layer that owns its machines as its source, its Timing option and a copy of those machines) with flattened state machines, states, transitions, conditions and the Parameter Driver, Tracking Control and layer control behaviours, motions (clips and blend trees), clips with their Cycle Offset, `activeSelf`, BlendShape weight and mesh renderer `enabled` curves for glTF node targets, curves for float FX parameter targets and mesh renderer material curves (a float, a color channel, or a channel of a texture's scale and offset) for glTF material targets, mesh renderer material slot curves for glTF node targets, Transform curves (local position, rotation and scale) for glTF node targets, and the count of what was left out by kind (`omitted`; a kind a newer exporter adds comes after the known ones, and the reader keeps it; a Gesture or Action controller, which comes after the FX, may have an `omitted` of its own, never empty, with only the kinds that change its transitions, `parameter`, `operation` and `unreadParameter`, then newer kinds, and the reader refuses one on the FX). Every FX parameter that a clip of the controller animates, under any state or blend tree, is a `parameter` target with the controller's default as `rest`: Unity then owns it, so menus, Parameter Drivers and the app do not change it, it is `rest` whenever no layer writes it, and a transition that waits for it sees the value of the previous evaluation. Unity moves only a float by a curve; a curve on an int, bool or trigger holds it at `rest`, so only float targets have tracks. A clip holds at most 16384 keys and 4096 tracks (`MaximumKeysPerClip`, `MaximumTracksPerClip`), given to `activeSelf` curves first, then to parameter curves, then to BlendShape curves, then to renderer `enabled` curves, then to material float curves (a material curve takes one track of that room as it is read, and when it becomes a track of several targets and those take the clip past 4096 tracks, it is left out with all its tracks), then to constraint `enabled` curves, then to material color and texture channel curves, then to material slot curves, then to Transform curves, so a kind written later never leaves out one written before; a curve past that room is counted as `other`, `parameter`, `blendShape`, `enabled`, `material` or `transform`. A count for `parameter` is a float parameter curve that did not fit the contract. The first key's in-tangent and the last key's out-tangent, which Unity never reads, are null when the clip holds a value that is not a number there. On an additive layer Unity adds a parameter track's value less its value at time 0, the reference pose it takes by default; a clip that names another reference pose leaves its parameter curves out, counted as `parameter`. An Avatar Mask is not written yet: Unity applies it to Transform and muscle curves only, and of those only Transform curves are written. A Parameter Driver operation carries `preventRepeats` (VRChat SDK 3.10.2 and later), true only on a random into an int; data written before it has none, which reads as false. Blend trees nest at most 32 deep (`MaximumBlendTreeDepth`; a tree of clips is 1 deep). Motions form a graph without cycles, not a tree: several blend trees may have the same motion as a child, and a motion expanded per parent holds at most 4096 motions (`MaximumExpandedMotions`). Only what Unity can take is written: Mute and Solo are already applied, a transition without a destination or with a condition Unity cannot read is left out, and the Any State transitions are those of the root machine alone, as Unity never takes one that a machine inside another holds. A condition's mode fits its parameter's type (`ConditionTypes`), blend trees, direct weights and a state's speed, cycle offset and time read floats and its mirror a bool. The parameter table is the Expression Parameters and the FX controller's parameters: a reference to anything else, or to a parameter of a type Unity does not read there, is written as a blend tree with no motion, a direct child left out or a state option unset. That is what Unity plays for a name the controller does not declare, but for a tree held by another tree, which Unity plays by what the other children leave; that case and a parameter of another type, where Unity reads an unrelated float, are counted as `unreadParameter`. A Parameter Driver operation on an undeclared name, or a copy without a source, is counted as `operation`. Menu controls name Expression Parameters only. A player starts a layer in its default state and looks at the root's Entry transitions only when the layer comes back through Exit, looks at the root's Any State transitions before those of the current state, and takes a machine's Exit transitions in order. An `active` target is a node's `activeSelf` (`rest` 0 or 1). A `morph` target is one morph target of the node's mesh, numbered as in `morphTargetBinds`: its curves hold the Unity weight `v`, and the glTF weight is `(v - baked) / (end - baked)`, taken after the layers are blended and not clamped. `baked` is the weight the base geometry already holds and `end` the weight the target shows at 1. When the base already holds a shape at the weight its target shows at 1, so that target shows no change, the export adds a morph target named `__VRVlog_Reverse_` and a hash that takes the base back to weight 0, and the target points at it with `end` 0, unless every curve holds the shape where the base has it. Its `rest`, like an `active` target's, is what it shows when no layer writes it, the value in the scene. A curve that holds `rest` is written too, as the reader weighs what the FX writes against the faces, but a target whose curves all hold `rest` on a base that shows it (`baked` equal to `rest`) is written only when its morph target is in the file for another reason, as it changes nothing by itself; a shape whose output is unknown (missing, made from several shapes that disagree, a target that shows no change and has no reverse target, a shape of several frames, which need not be linear, a lip sync shape, whose base geometry also takes the other lip sync shapes and the default mouth off, one that a clip of an additive layer moves, whose reference pose is not carried, or one that another mesh also has where the FX does not move it, once it is on another renderer after optimization, as a merge may have put that mesh's shape into the same output) is counted as `blendShape`, as is every shape when they would take the extension past its size limit, and a curve on a mesh with no node in the file as `missingNode`. How a morph target combines with the VRM expressions on the same target is up to the reader. An `enabled` target is the enabled flag of `component` on the node (`rest` 0 or 1); component `renderer` is the mesh renderer the node draws, which shows only while the node and its parents are also active; a renderer that is off or under an inactive object when the file is written is no mesh in the file, and its curves are counted as `enabled`. A `materialFloat` target is the float shader property `name` of glTF material `material` (`rest` its value in the scene); it has no node. A `materialColor` target is channel `channel` (`r`, `g`, `b` or `a`) of the color property `name`, and a `materialTextureST` target channel `channel` of the scale and offset of the texture property `name` (Unity's `name_ST`: `x` and `y` the scale, `z` and `w` the offset); each is one float like `materialFloat`. A `materialSlot` target is material slot `slot` (a submesh) of the mesh on `node`; `rest` and every key are the index of the glTF material the slot draws with, -1 for none. It is never interpolated (`Target.Stepped`): in a blend tree it takes the value of the motion of the greatest weight, and over a transition, a layer or the FX weight the next value once its weight passes 0.5. A slot curve is written only when every material it sets is one the file writes for some slot of a renderer it keeps (the exporter does not add materials yet), and of official lilToon; one that sets a material of another shader is counted as `materialSlotShader`, one that sets a material the file does not write as `material`, and one on a renderer the file has no mesh for as `missingNode`. Unity moves a renderer's material property on every material of that renderer, so a curve becomes a track of each target of a material the renderer draws with that the file writes and that has the property, and renderers that share a material share its target. Whether a material has the property and its `rest` are read from the material the avatar holds (lilToon), not from the fallback the export writes in its place. A material curve moves only a property that `LilToonFullContract` keeps for the app's material under the same name and type: a curve on another name or type is counted as `materialProperty`, and one on a feature switch the app fixes when it loads the material (`LilToonFullContract.Switches`, such as `_UseEmission`) as `materialSwitch`. A material curve that reaches no target, one on a target that a clip of an additive layer moves, a second curve of the same clip on a target, and a vector channel curve are counted as `material`; an `enabled` curve on a particle, trail or line renderer is counted as `enabled`. A `translation`, `rotation` or `scale` target is channel `channel` of the local position, rotation or scale of `node`, in Unity's space as the curve holds it (not glTF's), with `rest` its value when the file is written; each is one float. `translation` and `scale` name `x`, `y` or `z`. A `rotation` without `euler` is a quaternion channel (`x`, `y`, `z` or `w`, Unity's `m_LocalRotation`) that a reader blends as written and normalizes; one with `euler` true is an angle in degrees (`x`, `y` or `z`, Unity's `localEulerAnglesRaw`, `Target.Euler`) that a reader blends as an angle and turns into a rotation with `Quaternion.Euler`, and its `rest` is the angle the inspector shows. The rotation targets of one node are all Euler or all quaternion: a node the controller rotates both ways has its rotation curves counted as `rotationMixed`. A Transform curve that a clip of an additive layer plays is counted as `transform`, as Unity adds it to the pose. A Transform curve on a Humanoid bone is counted as `humanoidTransform`, and one on the avatar root, of another rotation interpolation or on a node the file does not have as `transform` or `missingNode`. Component `constraint` is a Unity or VRC constraint that `VRVLOG_avatar_constraints` writes: the target has `node` (the node the constraint moves), `property`, `component`, `index` (its entry in that extension's `constraints`) and `rest`, and no other keys; `Target.Index` holds the entry. Two constraints on the same node are two targets, and no two targets name the same entry, whatever their nodes. A curve on a constraint the file does not write there (converted to `VRMC_node_constraint`, or left in its pose without the extension) is counted as `enabled`. A target of any other `property`, or an `enabled` target of another `component` (which is always a string), is a kind a newer exporter may write: `Read` takes it without looking at its other keys (`Target.Known` is false, `Node` -1, `Rest` its `rest` when that is a number and 0 otherwise, `Fields` its keys as read), clips may move it and the evaluator gives it values, but a player writes it nowhere, and `Write` writes its keys back unchanged. `expressions` lists the custom expressions of the file (VRMC_vrm `expressions.custom`) whose clip the FX plays, each with the clips it was read from and the ways into the states that play one of them, directly or in a blend tree: the layer's default state (`default`), an entry transition of a machine (`entry`, with `machine`), an Any State transition (`any`) or a transition of another state (`state`, with `fromState`), each with that transition's conditions, the parameter values that show the face. A transition into a machine is not followed, so a state reached only through one is not listed; in a blend tree, how much of the face shows also depends on the tree's parameters. Except for targets of other kinds, `Read` rejects the whole extension when anything is outside the contract, and `Write` runs the same checks. The JSON schema is `Schema/VRVLOG_avatar_animator.1.schema.json`.
- `AvatarConstraintsData` (`VRVLOG_avatar_constraints`): reads and writes the Unity and VRC constraints the export leaves in their current pose because `VRMC_node_constraint` cannot express them (several sources, partial weights, Scale, Parent with offsets, Solve In Local Space and the like), with their settings as authored, for the app to solve the way Unity does. Each entry is one component: the node it moves, `type` (`position`, `rotation`, `scale`, `parent`, `aim`, `lookAt`), `origin` (`unity` or `vrchat`), its `enabled` flag (what FX curves turn on and off), Is Active, Locked, weight, VRChat's Solve In Local Space and Freeze To World (false for `unity`), its sources with their nodes and weights, and the axes, rest, offsets and aim or look-at settings of its type and no others. Vectors are `[x, y, z]` in Unity's frames as the editor shows them, Euler angles in degrees. A constraint whose target or a source the file has no node for, whose up object has no node while its settings read it (`worldUpNode` is -1 otherwise), whose target the export moved under a source, or whose target a VRM constraint moves, is not written and keeps its pose. `Read` rejects the whole extension when anything is outside the contract, and `Write` runs the same checks. The JSON schema is `Schema/VRVLOG_avatar_constraints.1.schema.json`.
- `AvatarPhysBonesData` (`VRVLOG_avatar_physbones`): reads and writes the avatar's VRChat PhysBones with the settings the app needs to feed the parameters VRChat writes for them (`<parameter>_IsGrabbed`, `_IsPosed`, `_Angle`, `_Stretch`, `_Squish`). The swing itself stays the VRM SpringBone. Each entry is one PhysBone, enabled or not and not under EditorOnly, whose root the file has a node for: the root's node, the parameter prefix (empty when none), Max Stretch and Max Squish without their curves, whether grabbing and posing are allowed, and `limitAngle`, the angle in degrees at which `_Angle` reads 1 (180, as VRChat normalizes it). FX parameters of the names the entries give, and only those, are `VRVLOG_avatar_animator` parameters with origin `builtin`.
- `AvatarContactsData` (`VRVLOG_avatar_contacts`): reads and writes the avatar's VRChat Contact Senders and Receivers with the shape, tags and parameter the app needs to solve their overlaps and feed the Receivers' parameters. Each entry is one component, enabled or not and not under EditorOnly, in hierarchy order: the node it hangs from (its Root Transform's, or the nearest written ancestor's, or -1 for the model space), `sphere` or `capsule` with its radius, whole height, position and rotation in that node's space, its collision tags, and whether it is active as exported (its object active and its component enabled); a Receiver adds its type (`constant`, `onEnter`, `proximity`), parameter, Allow Self, Allow Others, Local Only and Min Velocity. At most 64 Receivers and 4096 Senders are written; more are counted in `omitted` as `contactLimit` and `senderLimit`. `omitted` also counts contacts of a shape or Receiver Type the exporter does not know (`unknownShape`, `unknownReceiverType`), tags past the first 64 or longer than 1024 characters (`tagLimit`) and Receivers whose parameter was longer than 1024 characters (`parameterLength`); a reader keeps a kind a newer exporter adds after these.
- `AvatarAnimatorEvaluator`: plays `AvatarAnimatorData` without Unity, so the app can show what the FX, Gesture and Action controllers show. They play as VRChat's playable graph does (M15): Gesture, Action, then FX on top, each controller's layers seeing only its own and the controller blending over the ones before by its playable weight (`PlayableWeight`, 1 at the start and 0 for Action), which a Playable Layer Control behaviour sets. `LayerCount` and the layer methods count the layers of every controller that plays in one list, the FX's first, so an FX layer keeps its index; `LayerIndex(controller, layer)` gives a layer's place in it, -1 for a skipped controller. A layer's mask keeps it off the muscles of the body parts it leaves out, and the FX applies no muscle when its base layer has no mask (M16); the mask's transforms are not applied yet. The host sets parameters, calls `Advance` once a frame and writes `Values` (one per target, not clamped) to the targets; `HostShare` gives, per target, how much of what lies under every controller (VRChat's Base, which is the host's own pose) is left in `Values`: the product of (1 - playable weight) over the controllers that wrote the target, 1 when none did. A controller that moves muscles writes every muscle of its mask, the rest where its clips have none, even at weight 0, so a host with its own pose writes a muscle whose share is under 1 as `Values + (pose - rest) * HostShare`; `CompareOverHost` in `Tests/AnimatorComparison` checks that against Unity with a controller holding a pose under the Gesture. The share is meant for muscles: a muscle no clip moves has no target, so the host keeps its pose there although Unity would show the rest under a controller at weight 1; for other kinds it is given but VRChat's Base does not write them; a `morph` target's value is the Unity weight, which the host turns into the glTF weight with `baked` and `end`; `Advance` allocates nothing. While nothing can change the next frame (no layer in a weight blend or in a transition whose two sides give different values, no parameter set to a new value or changed by the frame, no state playing a motion whose values change over time, and the last frame giving the values of the one before), `Advance` only moves the states' times and the transitions' progress on and sets `Changed` to false: `Values` are as they were, and the host need not write them. A transition used as a timer (both sides give the same values) and a pending exit time are skipped too: `Advance` evaluates the frame in which the transition would end or the exit time would be crossed, computed with the same arithmetic as an evaluated frame, so it is the same frame at any frame time. Every frame of a run that skips matches a run with `SkipsSettledFrames` false, which evaluates every frame; `Tools/run-avatar-animator-evaluator-tests.ps1` checks that on the comparison cases, and with `-Vrm` on exported files. `SetLayerWeight` sets a layer's weight from the next `Advance`, as Unity's `Animator.SetLayerWeight` does (each controller's base layer stays at 1); the comparison with Unity drives weights through it. `Supports` tells whether the data can be played as Unity plays it: it refuses data with `parameter`, `operation` or `unreadParameter` in `omitted`, as those change which transitions fire, and an FX with additive layers, a synced layer with Timing, blend trees of a kind it does not know or a random with `preventRepeats`; the constructor throws for the same data. A Gesture or Action controller with one of those, or with one of those kinds in its own `omitted` (what the exporter left out while reading that controller; the root `omitted` holds the FX's, the other kinds and those of the extension as a whole), is not refused but skipped (`SkipReason` tells why), and the FX plays as it does without it. A `parameter` target is played as Unity plays a float parameter a clip animates: `Get` returns what the layers wrote (the controller's default when none did, and always for an int, bool or trigger), `Set` and Parameter Drivers do not change it, and transitions see it a frame later. Its source marks each timing and blending rule M1 to M14. M1 to M7 and M11 to M14 (the weights of 2D Freeform Cartesian, Simple Directional and Freeform Directional trees) are measured: the EditMode tests in `Tests/AnimatorComparison` record Unity 2022.3's Animator on generated controllers at 60 fps, 30 fps and an uneven frame time, and `Tools/run-avatar-animator-evaluator-tests.ps1` replays those recordings (`Tools/Fixtures/AvatarAnimator`) against the evaluator together with its own tests. M8 and M10 are VRChat behaviours (Parameter Driver and layer control) that plain Unity cannot record, and M9 (a state without a motion is 1 second long) has no recording yet; those three stay assumptions, as do M15 and M16, which follow VRChat's documentation and SDK and are not measured yet. A Parameter Driver's operations apply once every layer has stepped, in the order the states were entered and with the values of that moment, so no transition sees them before the next frame (M8): that is when Unity's transitions see a change the VRChat SDK makes from `OnStateEnter`, as the export's check against Unity's Animator (`AvatarAnimatorCrossCheck`) measured. Whether VRChat itself plays it the same way is not measured. To record again, run the comparison tests with `VRVLOG_ANIMATOR_RECORDINGS` set to a folder and copy the files into `Tools/Fixtures/AvatarAnimator`.
- `HumanoidLimitData` (`asset.extras` key `VRVLOG_humanoidLimits`): reads and writes the muscle limits (Unity's `HumanLimit`: `min`, `max`, `center`, `axisLength`) the avatar's humanoid set for its own bones, by VRM 1.0 humanoid bone name. A player that drives the avatar by muscles builds its humanoid with these limits; bones the file leaves out keep Unity's defaults. The exporter writes only the shoulders and arms whose limits are not the defaults, and nothing for other avatars. The key is not an extension, so it is not in `extensionsUsed` or `VRVLOG_requiredAppVersions`, and a player that does not know it plays the file as before. The JSON schema is `Schema/VRVLOG_humanoidLimits.1.schema.json`; the decision is `Documentation~/decisions/2026-11-16-arm-rest-and-limits.md`.
- `AvatarFormatVersions`: the `asset.extras` key `VRVLOG_requiredAppVersions`, whose value maps each `VRVLOG_` extension in `extensionsUsed` to the lowest app version (`major.minor.patch`) that reads the written content, the table of those versions, and `Compare` for app versions.
- `LilToonFullContract` (`VRVLOG_materials_liltoon`): validates the lilToon material extension. `Switches` lists the feature switches the app fixes when it loads a material, and `RuntimeType` gives the type of a property the app's material keeps under the same name. `UnboundExtensionName` (`VRVLOG_materials_liltoon_unbound`, schemaVersion 1, `Schema/VRVLOG_materials_liltoon_unbound.1.schema.json`) names the extension with the lilToon records of the glTF materials that no primitive uses and that a `materialSlot` target of `VRVLOG_avatar_animator` sets: the exporter adds such a material at the end of the glTF `materials` with its MToon approximation, and the record, in the shape of a `VRVLOG_materials_liltoon` material whose textures index that extension's `textures`, goes here because `Validate` rejects a record no primitive binds. `Validate` does not read this extension, so an app that predates it keeps `VRVLOG_materials_liltoon`.
- `LilToon234Catalogue`: the lilToon 2.3.4 shader and property catalogue the contract checks against. It is generated by `Tools/generate-liltoon-catalogue.py`; do not edit it by hand.

The assembly `VRVlog.AvatarFormats` uses only `System` (`noEngineReferences: true`). It has no Unity Engine or Editor dependency, so the exporter and the app compile the same source.

## Adding it to a Unity project

Add the package from this repository's `Formats` folder with a pinned commit, in `Packages/manifest.json`:

```json
"com.vrvlog.avatar-formats": "https://github.com/VR-Vlog/VR-Vlog-Avatar-Exporter.git?path=/Formats#<commit>"
```

The assembly is auto-referenced, so scripts outside any assembly definition (`Assembly-CSharp`, `Assembly-CSharp-Editor` and their `-firstpass` variants) see these types. An assembly definition that uses them references `VRVlog.AvatarFormats` by name.

The exporter package (`com.vrvlog.liltoon-vrm-exporter`) already contains this folder. Do not install both in one project: the two copies define the same assembly name and fail to compile.

## Changing the format

The exporter and the app must accept the same data. A change here takes effect in the app only after the app updates the pinned commit, so open the app change together with the exporter change.

The app pins this package by commit, not by version. The `version` in `package.json` stays `1.0.0` and does not identify a format revision; the pinned commit does.
